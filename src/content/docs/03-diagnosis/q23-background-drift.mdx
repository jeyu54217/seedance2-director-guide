## 一句話

[Q4：注意力機制](../01-basics/q04-attention/) 的 Temporal Attention 窗口在高運動幅度時失效——[Q13：15 秒限制](../02-seedance/q13-15sec-limit/) 的 O(n²) 瓶頸迫使實際部署截斷窗口，大位移超出 [Q6：時間步調節](../01-basics/q06-timestep/) 位置編碼的捕捉範圍，背景 patch 跟丟。

## WHY：Temporal Attention 的窗口為什麼不夠大？

[Q4：注意力機制](../01-basics/q04-attention/) 定義 Temporal Attention 為「跨幀 token 互相看」——第 1 幀的背景 token 和第 5 幀的背景 token 透過 Attention 匹配，確保同一個背景區域在時間軸上一致。

匹配的數學基礎是 [Q6：時間步調節](../01-basics/q06-timestep/) 的位置編碼（空間+時間）——兩個 token 的餘弦相似度決定它們是否「是同一個東西」。問題：位置編碼的餘弦相似度在**小位移時靈敏、大位移時驟降**。快速運鏡（whip pan、快速 dolly）→ 相鄰幀之間同一個背景物體的位移過大 → 相似度低於匹配閾值 → Temporal Attention 判定「這兩個 token 不是同一個東西」→ 背景從這一幀開始「跟丟」。

## WHAT：O(n²) 讓問題更嚴重

[Q13：15 秒限制](../02-seedance/q13-15sec-limit/) 揭露了根本的運算瓶頸：Self-Attention 佔 DiT 運算的 76%（Wan2.1）到 60%（Mochi-1）。在實際部署中，Temporal Attention 的窗口不是無限大的——為了控制 O(n²) 運算量，窗口被截斷為有限幀數範圍。快速運鏡時，背景物體在幾幀之內就移出截斷窗口——Temporal Attention 連「試圖匹配」的機會都沒有。

[Q14：運鏡機制](../02-seedance/q14-camera-motion/) 的四層運鏡分析也提供反面證據：Temporal Attention 在**慢速運鏡**時表現良好（subtle push-in、輕微 handheld），因為位移小、窗口內幀數夠。快速運鏡是另一回事。

## HOW

### ComfyUI

- **CameraCtrl + FreeInit（預設參數）+ Tile ControlNet**：三連——CameraCtrl 提供 explicit camera path 約束，FreeInit 重設初期雜訊強化 Temporal Attention 一致性，Tile ControlNet 鎖定局部空間結構
- **Euler sampler**：[Q7：Flow Matching](../01-basics/q07-flow-matching/) 的連續時間路徑比離散 DDPM 平滑，減少幀間跳躍
- **Steps ≥ 25**：足夠的去噪步數給 Temporal Attention 充分機會修正匹配

### Seedance 2.0

- `@video1` 運鏡軌跡參考：透過 [Q11：@ 標籤](../02-seedance/q11-at-tags/) 和 [Q14](../02-seedance/q14-camera-motion/) 的參考影片運動提取，提供 explicit camera motion conditioning
- 慢速運鏡 > 快速運鏡：[Q14](../02-seedance/q14-camera-motion/) 的訓練視覺先驗也暗示——slow camera movement 在訓練數據中遠多於 fast whip pan

:::tip[🎬 導演要點]

快速運鏡 = Temporal Attention 的敵人。O(n²) 窗口截斷 + 位置編碼大位移失效 = 雙重打擊。

慢速 dolly-in > 快速 zoom。如果一定要快速運鏡：CameraCtrl + FreeInit + Tile ControlNet 三連 + Steps ≥ 25。

:::
