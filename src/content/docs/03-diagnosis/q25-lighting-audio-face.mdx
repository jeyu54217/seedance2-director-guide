## 一句話

三個環境陷阱：光一暗臉就變了、上傳的音樂被參考影片蓋掉、臉被 safety filter 擋住——各自有獨立根因，但都來自 Seedance 2.0 的架構特性。

## 陷阱一：光源改變面部

### WHY

[Q4：注意力機制](../01-basics/q04-attention/) 的 Cross-Attention 是導演操控模型的入口——token 透過 Query 查閱外部輸入的 Key/Value 來決定畫面內容。但這個機制有一個前提：**token 裡要有足夠的 visible features 讓 Query 去匹配**。

暗場景的問題出在 [Q2：潛在空間](../01-basics/q02-latent-space/) 的 VAE latent——低亮度區域的 latent 資訊密度本來就低（暗部細節被感知壓縮 f=8 抽象掉）。結果：Cross-Attention 的 Query 在暗場景 token 中找不到足夠的 Key/Value 來鎖定面部特徵，臉就跟著光源一起變了。

### HOW

- 多光照參考圖：`@image1` 亮光正面 + `@image2` 暗光側面，讓模型在兩種光照條件下都有參考點
- 替代方案：亮光生成後，後製調暗——避免模型在暗場景中自己「猜」臉部特徵
- [Q15：情緒理解](../02-seedance/q15-emotion/) 的機制也暗示：Prompt 中的光照描述（"soft studio glow, consistent key light"）會透過 Text Encoder 映射為對應的 latent conditioning，比讓模型自己處理暗場景更可控

## 陷阱二：音軌汙染

### WHY

[Q9：多模態融合](../02-seedance/q09-multimodal-fusion/) 的統一 DiT 架構同時處理所有輸入模態——但這也意味著優先級衝突。[Q10：雙分支架構](../02-seedance/q10-dual-branch/) 的 Audio Branch 在同時收到影片內嵌音軌和獨立上傳音訊時，**預設優先採用影片內嵌音軌**——因為它在 latent space 中與 visual branch 已有 temporal alignment。

結果：你上傳了乾淨的配音檔，但參考影片裡的背景雜音把配音蓋掉了。

### HOW

- 上傳前將參考影片**完全靜音**（不只是調低音量，是移除音軌）
- 如果參考影片的運鏡和音訊都需要保留：分兩次生成——先靜音影片取運鏡，再 @Audio1 上傳音訊

## 陷阱三：人臉阻擋 + 審查不穩定性

### WHY

2026 年 2 月 MPA（Motion Picture Association）事件後，ByteDance 部署了 aggressive safety filter。從 [Q12：三階段訓練](../02-seedance/q12-training/) 的 RLHF 機制來看：safety reward 在訓練中疊加進了推理 pipeline——不是外加的後處理過濾層，而是**直接嵌入生成流程**。這解釋了為什麼同一個 prompt 昨天能過、今天被擋：filter 不是靜態關鍵字清單，而是動態調整的。

從 [Q15：情緒理解](../02-seedance/q15-emotion/) 我們知道 Seedance 2.0 的 Text Encoder 能理解語意——但同樣的語意理解能力，在審查場景中變成了**LLM-based 意圖判斷**。不是過濾"裸體"這個詞，而是判斷整段 prompt 的意圖是否可能產生敏感內容。

Segmind 分析了 4,367 次 API 呼叫，**37% 被拒絕**。良性 prompt 被隨機標記、審查嚴格度每日波動——這是目前社群最大的痛點。

### HOW

- 原創角色（非真人照片、非公眾人物）通過率較高——filter 是 pattern-matching 已知身份，不是阻擋所有 realistic faces
- 網格覆蓋法（社群 workaround）：在參考圖上疊加細網格線，干擾 face detection 但不影響生成品質
- 極端情況：改用 Kling 3.0（內容政策較寬鬆）
- 不同平台的 filter 嚴格度不同——fal.ai 比 Dreamina 嚴格，TopView 比 Higgsfield 寬鬆

:::tip[🎬 導演要點]

三個陷阱的共同教訓：**不要讓模型在資訊不足的情況下自己做決定。**

- 暗場景 → 給多光照參考，不要讓模型猜
- 參考影片 → 先靜音，不要讓模型選
- 人臉 reference → 用原創角色，不要碰真實人臉

:::
